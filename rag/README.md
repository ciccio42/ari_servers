# RAG servers

The local RAGs of the demo, one server per knowledge base. A RAG server does the **retrieval**: the answer is
generated by the [LLM server](../llm/README.md), with the system prompt and the model of the RAG. The clients keep
one API: `POST /chat` of the LLM server with `"rag": "<name>"`.

```
 client ──POST /chat {"rag": "department_office"}──► llm_server :8010 ──POST /retrieve──► rag_department_office :8030
                                                         │                                  Qdrant, BGE-M3, reranker,
                                                         │                                  registers (planner: Ollama)
                                                         └── backend ollama ──► ollama_server :11500 (qwen3.6:35b-a3b-q8_0)
```

| Path | Content |
|---|---|
| [`../common/ari_servers/rag.py`](../common/ari_servers/rag.py) | the interface: `Rag` (abstract class: `load`, `retrieve`, `generator`, `describe`), `Retrieval`, `Generator`, `Chunk`, `RagConfig`, `RagService` (HTTP server) |
| `<name>/environment.yml` | conda environment `rag_<name>`: the dependencies of this RAG only |
| `<name>/<name>_rag/` | the package of the RAG: `server.py` (HTTP server), `rag.py` (class of the RAG), `config.py`, `utils/` (code of the RAG) |
| `docker/` | image `ari_rag_server` (Ubuntu + Miniforge, one conda environment per RAG), `entrypoint.bash`, `run.bash` |
| `../ollama/docker/run.bash` | Ollama in Docker, the local models of the RAGs, in `models/ollama` |
| `../rag_knowledge_base/<name>` | knowledge bases (indexes, chunks), not versioned |

## API of a RAG server
| | |
|---|---|
| `GET /health` | `{"status": "ok", "service": "rag_<name>", "loaded", "generator", "rag", "kb_dir", ...}` |
| `POST /retrieve` | `{"question", "history"}` → `{"rag", "chunks": [{"text", "source", "score"}], "system", "user", "answer", "drop_patterns", "retrieval_id", "generator": {"backend", "model", "temperature", "max_new_tokens", "options"}, "queue_s", "retrieve_s", ...}` |
| `POST /postprocess` | `{"retrieval_id", "answer"}` → `{"text", ...}`: the answer corrected by the RAG (only when `/retrieve` gave a `retrieval_id`) |

`system` and `user` are the messages of the model (system prompt; context and question); a non-empty `answer` is the
reply without the model (e.g. nothing retrieved); `drop_patterns` are removed from the answer. The LLM server keeps
the history of the conversation and gives it to `/retrieve` (`history`: the previous turns), for the RAGs that use it
(high_level_unisa rewrites the question with it). A RAG that checks the answer of the model returns a
`retrieval_id`: the LLM server sends the answer to `POST /postprocess` and replies with the corrected text
(high_level_unisa: the names checked against the context).

The retrieval takes the execution lock of the servers (embedding and reranker on the GPU); the LLM server takes it
during the generation, after the retrieval: neither waits for the other.

## Run (Spark)
From `ari_servers`:
```bash
bash ollama/docker/run.bash start                 # Ollama, container ollama_server (127.0.0.1:11500)
bash ollama/docker/run.bash pull                  # once: qwen3.6:35b-a3b-q8_0, about 38 GB in models/ollama
bash rag/docker/run.bash build                    # once: image ari_rag_server, every rag/*/environment.yml
bash rag/docker/run.bash start                    # the RAGs of rag_servers (servers.yaml), container rag_<name>
bash rag/docker/run.bash status
bash rag/docker/run.bash test department_office "chi era presente nella seduta del 29/09/2025?"   # only retrieval
bash rag/docker/run.bash logs department_office
bash run_servers.bash restart llm                 # the LLM server reads llm.rag_servers at the start
curl -X POST -H 'Content-Type: application/json' localhost:8010/chat \
  -d '{"conversation_id": "test", "message": "quali studenti hanno chiesto il passaggio di corso nel 2025?", "rag": "department_office"}'
```
`run_servers.bash` starts them too, in the order whisper, ollama, llm, tts, RAGs, rasa (`bash run_servers.bash start
ollama rag`). The first start of a RAG downloads its embedding model and reranker in `models/rag/.hf_cache`.

## A new RAG
1. `rag/<name>/environment.yml`, `name: rag_<name>`, with the dependencies of the RAG.
2. `rag/<name>/<name>_rag/`: `config.py` (a dataclass that extends `RagConfig`, section `rag_<name>`, env
   `RAG_<NAME>_<FIELD>`), `rag.py` (a subclass of `Rag`), `utils/` (the code of the RAG), `server.py` and
   `__main__.py` as [department_office](department_office/department_office_rag/server.py).
3. `config/servers.yaml`: section `rag_<name>` (port, `kb_dir`, generator), `<name>` in `rag_servers`,
   `<name>=http://localhost:<port>` in `llm.rag_servers`.
4. `bash rag/docker/run.bash build` (the image gets the new environment), `start <name>`, `bash run_servers.bash restart llm`.
